# SolidCraft 0.51.1 Python client evaluation

Decision: keep the CLI wrappers. The official Python API is useful, but is not a clean replacement for this repository's batch execution, result files and diagnostics. No runtime code or backend-check script is added. This is a source review; no SolidCraft process or package installation was run.

References below name the local, untracked `.codex-ref` snapshots, with line numbers. They are review inputs, not files to commit.

## Contract comparison

The checkout has `runtime/sc.py`, `runtime/paramkit.py`, `runtime/pharness.py`, `runtime/parametric_build.py` and `runtime/parametric_harness.py`; it has no `runtime/parametric/process.py` or `kit.py`. `runtime/sc.py:29–44` writes a command script, saves a `.sc` and a results file, and reports the process exit status, stdout, stderr and result-file diagnostics. `runtime/paramkit.py:24–40` and `runtime/pharness.py:19–29` also load a base design and return ordered results plus an error. The current wrapper defaults to 0.50.0 (`runtime/sc.py:3–10`); this evaluation concerns the supplied 0.51.1 sources and does not upgrade that default.

| Requirement | Official client evidence and assessment |
|---|---|
| Same engine commands | `python_src_solidcraft__session.py:64–70` forwards arbitrary command IDs and parameters through MCP `execute`. Generated methods also exist. Engine coverage matches in principle, but identical replies are not established: MCP `execute` has its own verbose response contract (`docs_mcp.md:484`). Arguments with a top-level `None` are omitted (`python_src_solidcraft__session.py:59–66`), and nonfinite floats are rejected (`python_src_solidcraft__encode.py:15–28`), unlike simply serializing our existing lists. |
| Ordered command lists | MCP has `batch`, reachable through `d.tool`, so batch support is not missing. Its documented defaults include rollback on failure, preflight checks, a failure envelope and restrictions on steps (`docs_mcp.md:485`). These must be reconciled with CLI `run`; looping over `d.call` is not an equivalent batch adapter. |
| Saving `.sc` | Available through `save(path=...)`; the tool has explicit overwrite/conflict behavior (`docs_mcp.md:540`; example at lines 104–115). Output folders must be allowed to the MCP server; `headless` allows the current directory and explicitly supplied paths (`python_src_solidcraft__session.py:185–192`). Saving is a separate operation, not a `run --save` contract. |
| `--results` JSON and `--json-out` | The Python transport returns MCP `structuredContent.result`, with notes and images separately (`python_src_solidcraft__mcp.py:81–96`). Session calls retain only the latest notes/images (`python_src_solidcraft__session.py:58–62`). There is no Python `run` facade writing the CLI results artifact. Serializing these replies would require defining and verifying compatibility with the existing ordered results/error envelope, including partial failure. Structured JSON alone does not prove CLI JSON parity. |
| `--in` base design | Supported: `headless(design=...)` passes `--in` to the MCP process (`python_src_solidcraft__session.py:185–192`). |
| Timeouts | The reviewed repository subprocess calls do not set execution timeouts. The client adds none: initialization and calls block on `stdout.readline()` without a deadline (`python_src_solidcraft__mcp.py:53–79`). The ten-second wait is shutdown only, followed by kill (`:101–108`); it cannot bound a stuck request. Any required execution timeout needs separate supervision and cleanup. |
| Error reporting | Tool and protocol failures raise `SolidCraftError`; missing structured replies are rejected (`python_src_solidcraft__mcp.py:64–96`). However, process stderr is discarded (`:40–50`), server exit becomes a generic message (`:70–72`), and tool error results are stringified into exceptions (`:93–95`). This loses diagnostics currently captured by our wrappers and needs an adapter to preserve structured failures and completed results. |
| Binary selection | Client discovery uses `SOLIDCRAFT_CLI`, then a bundled binary, then PATH (`python_src_solidcraft__mcp.py:22–34`). It does not implement our `SC_CLI`, `SC_RELEASES` and `SC_VER` selection. `headless(cli=...)` could receive our resolved CLI explicitly (`python_src_solidcraft__session.py:185–192`). |

The package's `solidcraft` executable does preserve CLI arguments, streams and exit codes: it delegates to the binary (`python_src_solidcraft__cli.py:20–41`). That is a packaging/discovery convenience for the existing subprocess approach, rather than a replacement through the Python session API.

## Process and installation requirements

No GUI or pre-existing daemon is required. `headless()` starts its own `solidcraft-cli mcp --structured --headless` process and closes it with the session (`python_src_solidcraft__session.py:119–131,185–192`; `python_src_solidcraft__mcp.py:37–50,101–108`). `session()` instead attaches to a running session daemon if found, otherwise starts headless (`python_src_solidcraft__session.py:201–215`). A future deterministic build backend should explicitly choose `headless()`, avoiding shared design state.

The distribution and import name are `solidcraft` (`python_README.md:1–9,24–30`), and the release wheels are named `solidcraft-0.51.1-py3-none-<platform>.whl` and bundle the matching CLI (`release-0.51.1.md:37`). The docs require Python 3.10 or later and only the standard library, so Python 3.12 satisfies the documented requirement (`docs_python-api.md:105–106`). The snapshot lists `python/pyproject.toml` in `paths.txt` but does not include its contents or generated bindings; direct package metadata verification is therefore unavailable. A source checkout without generated bindings raises ImportError (`python_src_solidcraft__session.py:15–20`).

Do not assume `pip install solidcraft==0.51.1` works from PyPI: although the README and MCP docs advertise it, the versioned release notes explicitly say publication is pending (`release-0.51.1.md:71`). The supported documented fallback is to install the platform wheel from that release, or use `uvx --from <wheel> solidcraft mcp`. GitHub CI with Python 3.12 should install a pinned release wheel for its OS/architecture and verify imports, bundled CLI execution and native dependencies. The release lists Linux glibc 2.35+ (`release-0.51.1.md:30–31`). Actual index availability, wheel metadata and runner compatibility were not tested here.

Update (checked against PyPI on 2026-11-27): `solidcraft` 0.51.1 and 0.51.1.post1 are published on PyPI, so `pip install solidcraft==0.51.1.post1` is available for CI; the parity checks above still decide whether it replaces the CLI wrapper.

## MCP for repository agents

`uvx solidcraft mcp` would expose command discovery, execution, measurement, design inspection, saving and rendering through a standard stdio MCP server, allowing agents to explore and check generated designs interactively (`docs_mcp.md:3–11,17–51,126–133`). It launches the same CLI via the package entry point; use the pinned wheel fallback until PyPI availability is verified. Bare MCP can discover a running GUI, so use `--headless` for isolated work. It does not supply catalogue dimensions or replace source citations and generator checks, and repository restrictions on vendor assets still apply. This evaluation does not configure or launch the server.

## Switching the default later

First implement an opt-in `SC_BACKEND=client` adapter behind the unchanged wrapper signatures, explicitly selecting our resolved CLI and isolated headless sessions. Preserve command parameter semantics, allowed output paths, save behavior, ordered results files, failure envelopes and diagnostics, and provide bounded execution where required. Keep CLI as the default while CI exercises both backends on the same pinned release. Add `tools/sc-backend-check` then: compare parsed JSON for a tiny command list, followed by separate coverage of base-design loading, saving/reopening, partial failures, invalid commands, overwrite handling and process timeout/cleanup. Check representative generator and parametric harness workflows as well; a tiny successful example alone is insufficient.

Only after those parity checks pass should a separate change make the client the default, retaining an explicit CLI fallback and pinning the package/binary together. `SC_BACKEND` has no effect in this change. For this documentation-only change, CI needs the normal repository lint/static checks; runtime parity and package installation remain prerequisites for a future backend change.
